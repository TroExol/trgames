# lucid — PRD и устройство игры

Единая точка входа в lucid — что это, как работает игра, как устроена, где что лежит, что открыто. Перед задачей по lucid читай этот документ; меняешь поведение — правь его в том же коммите.

Актуально на 2026-10-03, после итерации 1 второй версии (поле, зоны кубиков, экономика). Первая версия влита в `master` (PR #14), вторая — в `feat/lucid`.

Пути 1–5 — от `server/src/games/lucid/`, если не указано иное; `shared/` = `tools/shared/src/games/lucid/types/`. Раздел 6 — от `client/src/`.

## Словарь

Одно понятие — одно слово. В этом документе, коде, промптах и задачах агентам используй только слово из первого столбца. Новое понятие сначала добавь сюда. Глоссарий `CONTEXT.md` старше и местами расходится с кодом; при расхождении верен этот словарь.

## 1. Продукт

**Что это.** Онлайн-бродилка для компании друзей, 2–6 игроков; тему, события и оформление каждой партии генерирует нейросеть, механика одна для всех тем.

**Цель.** Первым дойти до Финиша и открыть сейф. Один вечер, 30–40 минут, доигрывания нет.

**Принципы:** нейросеть генерирует содержание, не механику (ADR-0001); сервер авторитетен, клиент шлёт только намерения (ADR-0002); эффект собирается из атомов с целью и условием, не выбирается из перечня (ADR-0003); сначала доступ по ссылке без учёток, под публичность уже заложены id игрока, учёт стоимости генерации, хранение темы (ADR-0005).

**Не-цели:** не realtime-adventure; без накопительной экономики и банкротства (один Ресурс); без подготовки к нагрузке заранее (партия — килобайты). Без аналитики (PostHog недоступен в РФ, свой учёт токенов). Расширяемость (новый атом/клетка/карта без переписывания движка) заложена сразу.

**Первая версия.** Входит: лобби 2–6 по ссылке; мир и события нейросетью, скелет трека кодом; тема от игроков, жеребьёвка кубиком; трек с развилками, кубик, движение, Ресурс, варианты с порогами; поле SVG в палитре темы; запасная партия при сбое генерации.

Отложено сознательно — проверяем интерес к партии без этого: карточный слой целиком, Слепки партий, порталы, капканы, цветные клетки-якоря; отсюда же 4 атома/цели в первой версии вместо более широкого словаря ADR-0003 — не дефект, а рез.

**Вторая версия** (решено 2026-10-03, `docs/lucid/OPEN-QUESTIONS.md`, «Вторая версия: механики «Большой бродилки»»): живые партии показали ~10 минут без решений, Ресурс не нужен. Берём из настолки «Большая бродилка»: открытое поле (тип клетки виден, событие скрыто), Лавку, «Тадам», красные/зелёные клетки, порталы, экономику ×3, трек ×2 с зонами кубиков, цели `AHEAD`/`CHOSEN`. Колода карт — кодом, модель даёт только названия. Четыре итерации: поле → «Тадам» → Лавка → доводка.

Решение заказчика 2026-09-23 по недоделанному (`docs/lucid/OPEN-QUESTIONS.md`): ролей у игроков нет, только ники, события упоминают игроков по нику (4.3); «скелет кодом» — не будет, выбор оставили за моделью, договорились мерить.

## 2. Путь игрока

1. **Ник.** Анонимный id при первом заходе, живёт в браузере; место в партии закреплено за id, не за соединением (`room/Party.ts:114-123` и `141-147`). В лобби ник можно сменить кнопкой «Сменить ник» — место и ответ про тему сохраняются (`room/Party.ts` `join`, ветка `existing`); после старта партии кнопки нет. Ник не длиннее 20 знаков (`LucidShared.NICKNAME_MAX_LENGTH`, после `trim`): сервер отклоняет длинный ошибкой `nickname-too-long`, поле ввода ограничено `maxLength`.
2. **Вход.** По ссылке или по коду из 4 цифр (как в Jackbox); списка комнат нет. Код показан в лобби партии и вводится на странице «Новая партия». `/lucid/lobby` создаёт партию и ищет её по коду (`find-party`), `/lucid` принимает по `partyId+playerId+nickname`. Код — только адрес для входа: uuid остаётся сидом генерации и ключом статистики.
3. **Тема.** Каждый предлагает (≤200 символов) или отказывается — оба варианта считаются готовностью, видно всем до розыгрыша.
4. **Запуск.** Только владелец (`init.ts:129`), от 2 игроков (`Party.ts:94-96`). Кубик выбирает тему среди предложенных по сиду партии, иначе — из 5 подсказок.
5. **Ожидание генерации.** «Мир» сразу, затем трек и события одним сообщением (4.2). Потолок 180 с (`init.ts:24`), дальше — запасная партия, честно в ленте.
6. **Ход.** Бросок доступен только `ctx.currentPlayer`, у остальных кнопки выключены; таймера хода нет.
7. **Событие и выбор.** Доступный по цене вариант — полноэкранная карточка (сворачиваемая, не закрываемая), ≤3 варианта. Окна выбора карты (Лавка, сброс, закон) сворачиваются так же. Остальные игроки видят те же варианты выключенными под строкой «Выбирает {ник}»; «не по карману» считается от Ресурса ходящего.
8. **Конец и «Сыграть ещё».** Дойдя до Финиша, игрок стоит там и со своего следующего хода пробует открыть сейф; победитель — тот, кто открыл (3, «Сейф на финише»). Тем же составом можно сыграть сразу, тема разыгрывается заново; истории партии нет.

**Особые случаи.** Опоздавший после старта получает `party-already-started`, зрителя нет. Отвалившийся через 30 с получает автопилота — кубик / первая развилка / первый по цене вариант (`room/autopilot.ts:6`), видно в ленте. Отклонённый ход (`applyMove`) состояние не меняет, причина — только в серверный лог. Ушедший неотличим от отвалившегося, автопилот может довести его до победы (у сейфа он бросает без доплаты); партия удаляется без подключённых и 5 мин без них (`room/cleanup.ts:9`), срок не перевзводится. Сбой при старте (`8fa7ab1`+`e49fd68`) не роняет сервер: не дошедшая до игры партия откатывается в лобби (`Party.abortStart()`) со строкой `lucid.ribbon.startFailed`, уже идущая — только лог (5.6, 10).

## 3. Правила и механика

### Ники игроков и имена карт
Ролей у игроков нет, только ники. События упоминают игроков по нику, но не привязаны к конкретному игроку (4.3). В ленте и в заголовках карты называются именем из `G.cardNames` (`LucidShared.cardName`, запасное — `LAW_TEXT`/`SHOP_TEXT`), как на экране: исходное имя карты в ленту не попадает.

### Трек, развилки, ход и кубик
Трек — граф без циклов от `startId` к `finishId` (`shared/track.ts:10-11`, `core/track.ts:26-109`). Развилка — клетка с `next.length>1`, ветки `FORK_BRANCH_LENGTH=2` сходятся обратно.

`ROLL` — кубик 1–6; дойдя до развилки раньше конца шагов, движение ждёт `CHOOSE_BRANCH`, остаток донашивается после (`core/movement.ts:27-52`). Атом `MOVE` развилку не спрашивает, берёт первую ветку — может двигать не того, чей ход. Игрок на финише вместо `ROLL` делает `OPEN_SAFE` (ниже, «Сейф на финише»).

Событие открывается только движением от своего хода (`reducer.ts`, `afterMove`); движение эффектом варианта новое событие не открывает. То же правило у законов цвета и портала: их эффект срабатывает, только когда ход своим движением (`ROLL`, `CHOOSE_BRANCH`, `CHOOSE_DIE`) закончился на клетке — `landOnCell` в `core/cells.ts`, зовётся из `afterMove`. Любое другое движение клетку не активирует: сдвиг законом или картой, эффект события (`MOVE`, `SWAP_WITH_FIRST`). Исключение — портал: если игрока сдвинули на число клеток (`stepBy` в `core/cells.ts`: атом `MOVE`, «Тропа», «Попутный ветер», «Попутка», «Рывок», «Обвал», «Толчок») и он встал на портал, его переносит на парную клетку. Постановка на клетку игрока (обмен с лидером, «Аркан», «Кошка») портал не запускает.

### Типы клеток
Тип клетки виден на поле сразу, исход события скрыт до посещения. Типы раскладывает код при построении трека (`core/cellTypes.ts`, `assignCellTypes`, зовётся из `buildTrack`), сидом партии; `ECellType` — `shared/types/track.ts`. Доли считаются от внутренних клеток без старта, финиша и порталов:

| Тип | Что делает | Доля |
|---|---|---|
| `EVENT` | открывает событие с вариантами (выше) | 35% |
| `GREEN` | сама ничего не даёт; смысл ей дают законы | 12% |
| `RED` | сама ничего не даёт; смысл ей дают законы | 12% |
| `LAW` | игрок тянет два закона, один кладёт в левую ячейку, остальные сдвигаются вправо, правый уходит в сброс; невыбранный — в сброс | 10% |
| `SHOP` | если у игрока не меньше 3 Ресурса — открывается Лавка (подраздел «Лавка и рука»); иначе в ленте «{ник}: в Лавке не по карману» и ход идёт дальше | 10% |
| `EMPTY` | ничего | остальное (~21%) |
| `PORTAL` | переносит на парную клетку | 4 клетки — 2 пары |
| `START` / `FINISH` | старт и финиш | по одной |

Формы на поле: событие — ромб, пустая — малый круг, зелёная и красная — круги с «+» и «−», `SHOP` — домик, `LAW` — шестиугольник, портал — двойное кольцо с номером пары, старт и финиш — квадрат с флагом и сейфом (подробнее — раздел 6; макет — `docs/lucid/mockups/cells.html`).

Порталы стоят на прямых клетках без развилок, по паре в каждой половине пути: первая пара — в первой половине, вторая — во второй. Клетки пары разнесены на 4–9 уровней глубины, то есть перенос не дальше 8 клеток (решение владельца, `OPEN-QUESTIONS.md`). Портал двусторонний: встал на любую клетку пары — оказался на другой. Клетка назначения не срабатывает (ни событие, ни цвет, ни обратный перенос); перенесённая клетка попадает в `G.visited`. В ленте — «{ник} проходит портал».

### Законы
Закон срабатывает по цвету клетки остановки, после броска, в начале или в конце хода (`core/lawEffects.ts`, `runLaws`). Зелёная и красная клетки сами ничего не дают.

| Закон | Когда | Что делает |
|---|---|---|
| «Урожай» | остановка на зелёной | Ресурс +5 |
| «Тропа» | остановка на зелёной | 7 клеток вперёд |
| «Второе дыхание» | остановка на зелёной | ходит ещё раз |
| «Добрый знак» | остановка на зелёной | случайное событие без беды |
| «Дурная примета» | остановка на красной | случайная беда |
| «Пошлина» | остановка на красной | выбор: отдать 3 Ресурса или отступить на 3 клетки |
| «Налог» | остановка на красной | отдаёт каждому другому игроку по 2 Ресурса (вдвоём — 4), не больше, чем есть |
| «Подножка» | после броска | забирает по 3 Ресурса у каждого, кого обогнал |
| «Шестёрка» | после броска | выпала 6 (на любом кубике) — пропустит следующий ход |
| «Дубль» | после броска | два одинаковых кубика — ходит ещё раз |
| «Пособие» | начало хода отстающего | Ресурс +3 |
| «Подарок» | начало хода отстающего | берёт карту Лавки бесплатно, если в руке меньше трёх; в ленте «закон «Подарок»: {ник} — берёт карту» |
| «Удача отстающего» | начало хода отстающего | случайное событие без беды |
| «Попутный ветер» | конец хода отстающего | 5 клеток вперёд |
| «Лотерея» | конец хода отстающего | бросает кубик, получает столько Ресурса |

Правила срабатывания одинаковы для всех законов:
- Законы идут слева направо по ячейкам. Каждый срабатывает не больше раза за ход (`turn.fired`).
- «Отстающий» — `ETarget.LAST`, единственный дальний от финиша. Ничья — закон не срабатывает. Законы начала и конца хода смотрят только на ходящего игрока.
- Законы цвета смотрят на `turn.landedCellId`, а не на текущую позицию.
- «Подножка»: обогнан тот, чья глубина на треке не меньше глубины клетки, откуда игрок начал бросок (`turn.from`), и меньше глубины клетки остановки.
- Движение законом («Тропа», «Попутный ветер») клетку не активирует; портал срабатывает. На развилке идёт первая ветка. Игрок у сейфа не двигается.
- Закон, которому нужно событие, ставит `turn.eventCellId` или `turn.lawEvent` и фазу `CHOICE`; после выбора ход продолжает тот же шаг, сработавшие законы пропускаются. Если вытянутое событие нельзя оплатить ни одним вариантом или вариантов нет, оно не разыгрывается: в ленту идёт «{ник}: событие «{название}» не по карману».
- Строка ленты: «закон «{название}»: {ник} — {что}».
- Вытянутое событие, которое игрок не может оплатить, всё равно открывает клетку: в истории клетки оно остаётся открытым.
- «Рывок», «Кошка» и законы движения на развилке идут по первой ветке.

### Зоны кубиков
Путь делится на три трети по глубине (`LucidShared.diceZoneForDepth`, поверх `regionForDepth`, `shared/track.ts`). Зона определяется по клетке, где игрок стоит в момент броска:

| Зона | Бросок |
|---|---|
| `ONE` (первая треть) | один кубик, как раньше |
| `PICK` (средняя) | два кубика на выбор: фаза `DICE`, ход `CHOOSE_DIE { dieIndex }`, фишка идёт на выбранное значение |

`rollAndMove` (`core/moves.ts`) в зоне `PICK` бросает оба кубика, кладёт их в `G.lastRoll` (`values`, `pending: true`), движение не выполняет; редьюсер ставит фазу `DICE`, пока ходящий не пришлёт `CHOOSE_DIE` (`pickDie`, затем `afterMove`). Автопилот берёт первый кубик (`dieIndex: 0`, `core/autoMove.ts`). `TRoll` (`shared/types/state.ts`): `values` — все кубики, `pending` — ждём выбора, `picked` — индекс выбранного. Ленточные строки: «выбрасывает 3 и 5» → «идёт на 5».

### События, цена, ресурс
Клетка `EVENT` — до 3 вариантов (`generation/schema.ts:59`): гарантированный (`cost`) или рискованный (`threshold`). Не по карману — ход отклонён; иначе Ресурс списывается, `threshold` — отдельным броском (`core/options.ts:7-45`).

Содержание событий направляет код пометками у клеток (4.3): платный вариант — у ~трети, «беда» (ни один вариант не даёт чистого плюса) — у ~четверти, FIRST/LAST — у ~четверти каждая. Провал рискованного варианта ощутимый: −1…−3 клеток, −2…−4 Ресурса или пропуск хода.

Исход варианта скрыт, пока не раскрыт. Единица раскрытия — **ветка** (`success`/`failure`) конкретного варианта конкретной клетки: без `threshold` ветка всегда `success`; с `threshold` — `success` при броске ≥ порога, иначе `failure` (даже без `failure` в контенте — ветка всё равно считается раскрытой, просто пустой). Раскрывает ветку тот, у кого она сработала; вторая ветка остаётся скрытой, пока на неё не попадёт кто-то другой (или тот же игрок позже, на этой же клетке). `condition`/`otherwise` — часть ветки, раскрывается вместе с ней целиком. Источник раскрытых веток — история клетки (ниже).

Карточка варианта (`EventCard/OptionButton.tsx`) под текстом показывает только раскрытые исходы: без порога — одной строкой без префикса, пока ветка не раскрыта — вовсе без строки (ветка одна, вопросительный знак под единственным исходом выглядел бы лишним драматизмом); с порогом — раздельно «удача — …» / «провал — …», нераскрытая ветка — «удача — ?» / «провал — ?» (знак вопроса, а не пустота: видно, что развилка есть, просто исход ещё не известен). Раскрытая, но пустая `failure` — «провал — ничего». Порог и цена видны всегда, независимо от раскрытия. Строит текст чистая функция `LucidShared.describeEffect` (`tools/shared/src/games/lucid/describe.ts`, экспорт через `LucidShared`): атомы через запятую общей подписью цели (ты/лидер/отстающий/все — не настоящий ник, целевой игрок ещё не известен), при условии — «если {клетка|ресурс} {=/>/≥/</≤} {value}: …, иначе: … (или «ничего» без `otherwise`)». `resourceName` карточка берёт из `state.G.theme.resourceName` (`Hud/index.tsx` → `EventCard` → `OptionButton`).

### История клетки

`G.cellHistory: Record<cellId, THistoryEntry[]>` (`shared/types/state.ts`) — все разыгранные варианты по клеткам, источник раскрытых веток. Запись (`THistoryEntry`): `playerId`, `nickname`, `optionIndex`, `branch: 'success' | 'failure'`, `roll?` (был ли бросок), `lines: string[]` — тот же прирост `G.log`, что породил этот выбор (сам выбор, бросок, применённые эффекты). Пишет `resolveOption` (`core/options.ts::resolveOption`) на клетку `player.position`, взятую до применения эффекта (эффект может увести игрока дальше атомом `MOVE`). `setup.ts` инициализирует `{}`; партии из базы старше этого поля читаются устойчиво — `Party.fromSnapshot` подставляет `cellHistory ?? {}` в снимок при подъёме из хранилища (5.6/5.7).

Сервер вырезает нераскрытое в `core/formatForPlayer.ts`: посещённые события уходят клиенту в форме `LucidShared.TEventView`/`TOptionView` (`shared/types/content.ts`, `shared/types/effect.ts`), не сырым `TEvent`/`TOption`. У варианта всегда видны `text`/`threshold`/`cost`; `success`/`failure` — только если соответствующая ветка раскрыта в `cellHistory` этой клетки. Поле `revealed: { success: boolean; failure: boolean }` отличает «раскрыта и пуста» (`revealed.failure=true`, `failure=undefined`) от «ещё не раскрыта вовсе» (`revealed.failure=false`). `cellHistory` целиком уезжает в `TStateForPlayer.G` — записи в нём и так существуют только для посещённых клеток (запись появляется вместе с посещением).

### Просмотр клетки

Клик по посещённой клетке с историей (`Board/index.tsx`, слой `onViewCell`, независимый от `onSelectCell` для развилок) открывает `CellView` (`PartyPage/components/CellView/index.tsx`) — заголовок, текст, варианты только с раскрытыми ветками (без кнопок выбора) и список истории строкой `LucidShared.describeHistoryEntry`: «Ваня — «Вскрыть ящик ломом», выпало 5 из 4 — заряды +3». Кликабельны только клетки, где `cellHistory[cellId]` не пуст — это само собой исключает и непосещённые клетки, и клетку текущего нерешённого события (запись появляется только после выбора), поэтому просмотр никогда не мешает текущей карточке события: у неё своё независимое состояние в `PartyPage/index.tsx` (`viewCellId`), закрытие не трогает `Hud`.

Лента (`G.log`) после `CHOOSE_OPTION` получает по порядку: «{ник} выбирает «{текст варианта}»» (`core/options.ts::resolveOption`, до броска), затем строка броска (уже была), затем по строке на каждый применённый атом — с реальными никами целей, не общей подписью (`core/atomLog.ts::describeAtomLog`, использует `LucidShared.describeAtomAction` и `resolveTarget`): «Петя: +2 клетки», «Петя, Ваня: заряды −1», цель `ALL` — коротко «все: …», не перечисление. Ничья `FIRST`/`LAST` (`resolveTarget` вернул `[]`) — «лидера нет — ничья, никого не задело» / «отстающего нет — ничья, никого не задело». `SWAP_WITH_FIRST` — свой текст: «Ваня меняется местами с Петей» либо «обмена нет: лидер — сам игрок» / «обмена нет: ничья». Эффект без атомов к применению (условие не прошло и `otherwise` нет, либо `threshold` провален и `failure` нет) — «ничего не произошло» (`core/effects.ts::applyEffect`, `core/options.ts::resolveOption`).

Ресурс — один счётчик, старт `START_RESOURCE=10` (`core/setup.ts:6`), не ниже нуля — Долг. Ни один вариант не по карману — событие пропускается.

### Показ броска

Сервер присылает состояние уже после броска — фишка сразу стоит на новой клетке. Клиент не применяет такое состояние мгновенно: `PartyStore.applyView` (`client/src/routes/games/lucid/PartyPage/stores/PartyStore.ts`) сравнивает `G.lastRoll` предыдущего показанного вида и нового пришедшего через `isNewRoll` (`stores/rollReveal.ts`) — по `TRoll.stateId` (версия состояния, в которой бросок случился, клеймит `applyMove` — `server/src/games/lucid/core/reducer.ts`, поле опционально в `TRoll`, `tools/shared/src/games/lucid/types/state.ts`), а не по значению: два броска подряд могут выпасть одинаковыми, и сравнение по числу ничего бы не показало. Клеймо ставится, только если `next.G.lastRoll` — новый объект (сравнение по ссылке с `state.G.lastRoll` до хода): `rollAndMove` и `resolveOption` всегда создают его заново, `takeBranch` и пропуск хода — не трогают, значит и не переклеймляют. Бросок без клейма (сделан до появления поля, партия поднята из базы) считается старым и не проигрывается: сравнение по ссылке заново показывало бы его на каждом обновлении — при пропуске хода фишка проходила по старому броску и возвращалась на место.

Если новый бросок найден, `view` (то, что видят компоненты) не меняется сразу — стор ждёт: кубик 700 мс «катится» (`Die` перебирает грани локальным интервалом, `spinning=true`), затем 500 мс держит выпавшее значение (`pendingRoll`, `dicePhase='settled'`), и только потом применяет пришедшее состояние — позиции, карточка события, итог, лента читают `view`, и до этого момента видят предыдущее. `prefers-reduced-motion` сокращает это до одной паузы в 400 мс с сразу показанным числом, без перебора граней и без пошагового хода (`prefersReducedMotion()` в сторе). Первое состояние партии (подключение, восстановление после реконнекта — `view` до этого `undefined`) и ходы без нового броска (например `CHOOSE_BRANCH`) применяются сразу, без паузы.

Пока идёт показ, `PartyStore.isRevealing` (`dicePhase !== 'idle'`) держит кнопки хода (`Hud`: «Бросить кубик», кнопки развилки, варианты события) и клик по клетке развилки на поле (`PartyPage/index.tsx`, `isMyBranch`) выключенными — нажатие по ещё не применённому виду не ушло бы никуда полезного.

Несколько пришедших подряд состояний не копятся в очередь: `applyView` при новом вызове обрывает текущий показ (`clearTimers`) и досказывает историю от последнего реально показанного `view` к самому свежему пришедшему. Очередь честнее показала бы каждый бросок по отдельности, но при частых состояниях (автопилот на несколько игроков подряд) отставание только растёт; обрыв и пересчёт всегда возвращают к актуальному состоянию за фиксированное время — выбор в пользу этого варианта.

После показа значения, если бросок — движение хода (`roll.threshold === undefined`, не проверка порога варианта), фишка идёт по клеткам пути пошагово: `walkPath` (`client/src/lib/lucid/walkPath.ts`, чистая функция, повторяет остановку `core/movement.ts::walkForward` на развилке или тупике) считает путь от текущей показанной позиции игрока на нужное число шагов, и стор выставляет позицию по одной клетке каждые 150 мс, поверх иначе неизменного `view` (карточка, итог и лента всё ещё ждут). Для всех прочих случаев — порогового броска варианта, эффекта `MOVE` (в том числе с минусом), `SWAP_WITH_FIRST` — путь неочевиден, и после паузы `view` применяется сразу целиком; плавность даёт не JS-анимация позиции, а CSS-переход `cx`/`cy` токена в `Board` (`TOKEN_TRANSITION_MS=150`, выключен при `prefers-reduced-motion`) — он же сглаживает и промежуточные шаги пошагового хода.

Два кубика (зона `PICK`, раздел 3, «Зоны кубиков»): `Die` рисует две грани (`TRoll.values`), при катании крутятся обе. Какие шаги показывать, решает чистая `revealPlan(roll)` (`stores/rollReveal.ts`): `spin` — крутить ли кубик (не крутить, если бросок уже содержит `picked` — кубики показаны при первом броске, выбор их не перебрасывает), `walk` — идти ли фишке (не идти, если бросок — проверка порога варианта или `pending`, то есть ждём выбора). В фазе `DICE` у ходящего две кнопки «Идти на N» (`Hud`, `handleChooseDie` → `CHOOSE_DIE`), у остальных — строка «{ник} выбирает кубик»; на кнопке броска в зоне `PICK` подпись «Бросить: 2 кубика · выбор». Цифра рядом с кубиками: пока выбор не сделан — нет (`pending`), после выбора — выбранное значение, невыбранная грань притушена (opacity 0.35) (`e9bf5a3`).

Лента и звук синхронизированы с тем же показом, не с приходом сокет-события:

- `appendRibbon` — отдельное сокет-событие, сервер шлёт его после `update-party` в одном и том же `broadcast()` (`server/src/games/lucid/init.ts:375-386`), но раньше, чем клиент применит новый `view`, потому что применение специально задержано. `PartyStore.appendRibbon` копит строки в `pendingRibbon`, пока `isRevealing`, и выпускает их в `ribbon` тем же вызовом, который коммитит `view` (мгновенно — если брос­ка не было, в конце показа — если был); при обгоне одним показом сразу нескольких пришедших состояний (см. «не копится в очередь» выше) строки всех пропущенных обновлений копятся и выходят разом с финальным `view`, тем же порядком, в котором пришли.
- Звук 'dice' звучит в момент начала показа (`reveal()` — переход в `spinning`, а при `prefers-reduced-motion` сразу в `settled`), а не при финальном применении `view`: иначе бросок звучал бы на 1,2 с позже самого себя. Звук 'step' на пошаговом ходу звучит на каждый шаг из `walkSteps`, а не один раз на весь ход — `stateId` промежуточных `view` не меняется, и диф состояний в `PartyPage` (`services/LucidSoundService.ts` через `lucidSoundService`) его бы не увидел. Чтобы не озвучить тот же переход дважды, `PartyStore.revealedStateId` отмечает `stateId` view, для которого 'dice'/'step' уже отыграны по ходу показа — диф в `PartyPage` сверяется с этим полем и не кладёт их в очередь повторно; остальные звуки (`branch`/`resourceUp`/`resourceDown`/`event`/`win`) по-прежнему звучат диффом при коммите, показ их не трогает.

### Остаток шагов у развилки

Пока движение стоит на развилке и ждёт `CHOOSE_BRANCH`, `G.pendingSteps` — сколько шагов донашивается после выбора ветки. `Hud` (`renderAction`, фаза `BRANCH`) показывает это строкой «Осталось N шагов» с русским склонением (`pluralizeSteps`, `client/src/lib/lucid/pluralize.ts`, чистая функция с тестом) — видно всем игрокам, не только тому, чей ход: у ходящего строка идёт частью подсказки «Выбери, куда свернуть», у остальных — отдельной строкой под «Ходит {ник}».

### Сейф на финише
Дойти до `finishId` (броском, довыбором ветки, эффектом) — не победа: игрок стоит на финише, ход заканчивается как обычно, по позиции `reducer.ts` победителя не объявляет. Со своего следующего хода игрок на финише вместо `ROLL` делает `OPEN_SAFE { bonus: 0 | 1 | 2 }` (фаза `ROLL`): бросается один кубик, к нему прибавляется `bonus`, результат ≥ 5 — `G.winner`, фаза `ENDED`; иначе ход переходит дальше, фишка стоит. Константы — `shared/safe.ts`: порог `SAFE_THRESHOLD=5`, цены `SAFE_BONUS_COSTS=[0, 5, 10]`, нужное значение кубика `safeNeed(bonus)`; клиент берёт подписи оттуда.

Доплата: `bonus` 1 стоит 5 Ресурса, 2 — 10; списывается до броска, при провале сгорает, действует только на эту попытку. Сервер отклоняет ход, если `bonus` не целое 0…2, Ресурса не хватает, игрок не на финише, фаза не `ROLL` или ход не его. Обычный `ROLL` на финише отклоняется. Пропуск хода (`skipTurns`) пропускает и попытку: `OPEN_SAFE` тратит счётчик вместо броска и ничего не списывает (`reducer.ts`, `skipTurn`).

Иммунитет: игрока на финише не сдвигают и не меняют местами эффекты — защита в атомах (`core/atoms.ts`, `isAtFinish`): `MOVE` обходит такого игрока при любой цели, `SWAP_WITH_FIRST` не происходит, если лидер на финише (или сам игрок на нём); в ленте «обмена нет: игрок у сейфа неприкосновенен». `RESOURCE` и `SKIP_TURN` действуют как обычно. Порталы финиша не касаются.

Бросок у сейфа кладётся в `G.lastRoll` как проверка порога: `value` — кубик, `threshold` — `safeNeed(bonus)`; клиент крутит кубик (`revealPlan`: `threshold` задан — фишка не идёт), под кубиком «порог N · взят/не взят». Лента: «{ник} бросает за сейф: 3 — не открыл», с доплатой — «{ник} платит 5 и бросает за сейф: 3 + 1 = 4 — сейф открыт». Автопилот: `OPEN_SAFE { bonus: 0 }` (`core/autoMove.ts`). Решение — `OPEN-QUESTIONS.md`, «Финиш-сейф».

В фазе `ROLL` у ходящего на финише `Hud` вместо «Бросить кубик» показывает три кнопки: «Открыть сейф · нужно 5+», «+1 за 5 · нужно 4+», «+2 за 10 · нужно 3+» (недоступные по Ресурсу выключены); остальным — строка «{ник} открывает сейф».

### Перекос в пользу отстающих, пропуск хода

Перекос в пользу отстающих — завязки «удар по лидеру» / «помощь отстающему» раскладывает код (`generation/premises.ts`), а вот механику под них пишет модель; результат код не проверяет. Рядом с ними код раздаёт пометку «беда» (все варианты с потерей) — на тех же клетках, где нет этих двух завязок, чтобы ни одна клетка не требовала противоположного. Перенести в код — открытый вопрос, решено оставить и мерить (`docs/lucid/OPEN-QUESTIONS.md`, «"Скелет кодом" не сделан»).

Пропуск хода — счётчик `skipTurns`, тратится вместо броска по одному, не уходит в минус.

### Лавка и рука

Остановка на `SHOP` с Ресурсом не меньше 3 открывает Лавку: из колоды Лавки (`G.cards.shopDeck`) выкладываются три карты (`G.cards.shopOffer`), фаза `SHOP`. Игрок ходом `BUY_CARD` покупает одну (`index` — индекс в `shopOffer`) или отказывается (`index: null`). Покупка списывает 3 Ресурса и кладёт карту в руку; остальные карты уходят в сброс (`shopDiscard`). Отказ: все три в сброс, Ресурс цел. После хода игра идёт дальше (`proceed`). Окна выбора карты — Лавка, сброс при полной руке и выбор закона (`CardPick`) — сворачиваются кнопкой «Свернуть», как событие: в нижней панели остаётся полоса `EventBar` («Лавка», «Сброс карты», «Выбор закона») с кнопкой «Развернуть». Свёрнутость привязана к `stateId` и шагу окна (`Hud`, `collapsedPick`): новое окно открывается развёрнутым.

- Рука — не больше трёх карт. При полной руке покупка требует `discardUid` — карту из руки, которая уходит в сброс; без неё ход отклоняется. Не хватает Ресурса или индекс не целое число — ход отклоняется.
- Пустая колода собирается из сброса и тасуется (`drawFrom`, общий для законов и Лавки).
- Колода Лавки — 20 карт, по две каждого `EShopCard`; `uid` 0…19 различает копии. Названия и правила — `SHOP_TEXT`.
- Закон «Подарок» берёт карту из колоды Лавки без цены, если в руке меньше трёх (`giveCard`).

| Карта | Вид | Правило |
|---|---|---|
| «Подкова» | пассивная | остановился на пустой: Ресурс +4 |
| «Обвал» | активная | ближайший впереди отступает на 6 клеток |
| «Толчок» | активная | выбранный игрок отступает на 4 клетки |
| «Аркан» | активная | ближайший впереди, если до него не больше 10 клеток, встаёт на твою клетку |
| «Кошка» | активная | встань на клетку ближайшего впереди, если до него не больше 10 клеток |
| «Утяжелённый кубик» | пассивная | +1 к броску на движение |
| «Громоотвод» | пассивная | остановился на красной: Ресурс +5 |
| «Рывок» | активная | пройди 5 клеток вперёд |
| «Попутка» | пассивная | остановился на пустой — пройди 4 клетки вперёд |
| «Порча» | активная | ближайший впереди в начале своего хода разыгрывает беду |

Пассивные карты работают без хода игрока (`core/passiveCards.ts`):

- «Громоотвод», «Подкова», «Попутка» срабатывают на шаге `LANDED` после законов, по порядку карт в руке, каждая раз за ход (`turn.used`). Смотрят на клетку остановки (`turn.landedCellId`). «Попутка» клетку остановки не активирует (портал срабатывает) и за одну остановку срабатывает один раз.
- «Утяжелённый кубик»: +1 к броску на движение за каждую такую карту в руке (`rollBonus`). Кубик показывает выпавшее число, фишка идёт на число + бонус; при двух кубиках бонус добавляется к выбранному. В ленте «{ник} идёт на {n} (+{бонус} от карт)». Законы «Шестёрка» и «Дубль» смотрят на выпавшие кубики без бонуса.

Фаза карт (`EPhase.CARDS`, шаг `CARDS` машины хода):

- Фаза открывается после клетки и законов конца клетки, только если у ходящего есть карта, которую можно сыграть (`hasPlayable`). Иначе ход идёт к концу.
- Ходы: `PLAY_CARD { uid, targetId? }` играет карту, `END_TURN` завершает ход.
- Каждая карта руки играется не больше раза за ход (`turn.used`). Активная карта одноразовая: розыгрыш бесплатный, сыгранная карта уходит из руки в сброс Лавки (`shopDiscard`), Ресурс не меняется. Карта пассивная или уже сыграна — ход отклоняется.
- Правила допустимости (`canPlay`, `hasPlayable`, `nearestAhead`) живут в `tools/shared/src/games/lucid/cardRules.ts`. Сервер проверяет ими ход `PLAY_CARD`, клиент (`Hand`) прячет ходы, которые сервер отклонил бы: кнопка «Применить» и список целей «Толчка» показываются только для допустимых ходов.
- «Ближайший впереди» — см. «Словарь». Расстояние — разница глубин (`trackDepths`). «Кошка» и «Аркан» требуют расстояние не больше 10. «Рывок» и «Кошка» не играются у сейфа.
- «Рывок» и «Кошка» клетку не активируют, ход возвращается в фазу карт. «Рывок», «Обвал» и «Толчок» на портале переносят на парную клетку, «Кошка» — нет.
- «Порча» увеличивает `cursed` у цели на 1. В начале хода проклятого игрока, до законов начала хода, `cursed` уменьшается на 1 и он разыгрывает беду (`drawEvent`, фаза `CHOICE`). Если бед в партии нет или ни один вариант не по карману, в ленте строка, ход идёт дальше.
- «Толчок»: `targetId` обязателен — другой игрок не у сейфа; он отступает на 4 клетки при любом числе игроков. Отличие от «Обвала»: цель любая, а не ближайший впереди.

Симуляция партий ботами — `server/src/games/lucid/reports/simulate.ts`, запуск `yarn workspace @trgames/server lucid:sim <base|skill|ablate|cards> <партий> [--generated]`.

Прочие элементы бывшего «карточного слоя»: долг (Ресурс не уходит в минус) — поведение атома `RESOURCE`; порядок игроков — цели `FIRST`/`LAST`.

## 4. Генерация партии

### 4.1 Кто что решает

ADR-0001: модель отвечает за контент, движок — за механику и структуру.

| Решает модель | Решает движок |
|---|---|
| Имя мира, ресурса, палитра, `mood` | Граф трека: развилки, схождение, длина (`core/track.ts`) |
| Названия/цвета регионов (3–5) | Разбивка клеток по регионам — по глубине пути |
| Название (≤30 знаков) и строка настроения (≤70) каждой из 25 карт: 15 законов и 10 карт Лавки | Правило карты: пишет только код (`LAW_TEXT`/`SHOP_TEXT`); без ответа модели действуют запасные названия из `cardText.ts` (`cardName`) |
| Заголовок, текст события и вариантов | Набор атомов/целей и диапазоны значений (`generation/schema.ts`) |
| Атомы эффекта в диапазоне | Валидация, ретраи, бюджет, откат на запасную |
| `threshold`/`cost` варианта | Персистентность, стадийная трансляция, учёт usage |

Клетка скрыта до посещения (`shared/content.ts:12-14`); регионы по глубине пути считают и клиент (для поля — 6.4), и сервер (для края клетки в промпте — 4.3) одной и той же функцией `regionForDepth` (`@trgames/shared`, `games/lucid/track.ts`).

### 4.2 Стадии и порядок

Двухстадийна: «Мир», затем события. `CONTEXT.md`/ADR-0004 описывают три стадии с отдельным «Скелетом» — устарело, решено 2026-09-23 (`docs/lucid/OPEN-QUESTIONS.md`, «Генерация остаётся двухстадийной»).

| Стадия | Кто строит | Клиентам |
|---|---|---|
| «Мир» | Модель, один вызов | Сразу по готовности (`init.ts:135-138`) |
| Скелет трека | Код, детерминированно, внутри «Наполнения» | Не транслируется отдельно |
| Завязка и край клетки | Код, детерминированно от сида партии, до чанкования на куски (`generation/premises.ts`) | Не транслируется отдельно — только текстом в промпте события |
| «Наполнение» (события) | Модель, пачками параллельно | Одним сообщением со скелетом (`init.ts:142-151`) |

Трек строится дважды сидом `${uuid}:track` (`room/Party.ts:198`) — детерминированно. Завязка и край клетки — тоже код, а не модель: решение владельца 2026-09-23 против повтора содержания между параллельными кусками (`docs/lucid/OPEN-QUESTIONS.md`, «"Скелет кодом" не сделан», переоткрыт и частично решён тем же днём) — подробности 4.3. Фаза `GENERATING` даёт клиенту `theme` без `state`. На `:nitro` с выключенным рассуждением партия из 48 событий собирается за 13–18 с (было 49–134 с, медиана 58 с, с включённым рассуждением; замер — 4.6).

### 4.3 Промпты

`buildWorldPrompt(theme)` (`generation/prompt.ts:53-82`) просит `name`, `resourceName` (одно слово во множественном числе, без пробелов, ≤20 знаков), `palette`, `mood`, `regions` (3–5) и `cards` — название и строку настроения для каждой из 25 карт; промпт перечисляет карты под безликими ключами `card1`…`card25` (позиция в `PROMPT_CARD_IDS` — законы, затем карты Лавки) с правилом (слово «ресурс» вместо названия ресурса), правило модель не пересказывает. Ключи enum (`ROCKET`, `HAND_OF_FATE` и прочие) в промпт не попадают: иначе модель переводит их обратно в названия карт исходной настольной игры, а они запрещены. Названия попадают в `TPartyContent.cardNames` и `G.cardNames`, клиент получает их в `formatForPlayer`.

`buildEventsPrompt(themeName, resourceName, cells, nicknames)` (`prompt.ts:106-180`) — по событию на клетку из `cells: TEventCellBrief[]`, не на голый номер: каждая строка — «клетка N — край «...», завязка: ...» (`describeCells`, `prompt.ts:53-59`). Завязка и край собирает код до вызова промпта (`generation/premises.ts`), не модель:

- `assignPremises(cellIds, seed)` — 12 завязок общего пула («находка», «ловушка», «встреча с незнакомцем», «торг или сделка», «стихия», «поломка или препятствие», «развилка или выбор пути», «тайна или загадка», «соблазн», «погоня», «отдых или передышка», «общее бедствие») плюс две с требованием к механике, `PREMISE_LEADER` «удар по лидеру» (~четверть клеток, target `FIRST`) и `PREMISE_LAST` «помощь отстающему» (~четверть клеток, target `LAST`) — на этих двух в строку клетки добавляется «(хотя бы один вариант с атомом на FIRST/LAST — ...)». Раскладка — `shuffle` от `createRandom(`${seed}:premises`)` (`core/random.ts`) по всем клеткам партии разом, потом `spreadAdjacent` механически переставляет соседние совпадения без нового рандома — так соседние куски (параллельный `Promise.all` в `pipeline.ts`) не получают одну и ту же завязку на границе, и куски вообще не повторяют друг друга: до этой правки 5 из 8 кусков в замере получили заголовок «Соляной штиль» под один и тот же промпт (`docs/lucid/OPEN-QUESTIONS.md`). Поверх завязок код раздаёт ещё две независимые пометки (`TCellPremise.calamity` / `.paid`), каждую отдельным сидом (`${seed}:calamity`, `${seed}:paid`), так что раскладка завязок остаётся прежней: **«беда»** — ~четверть клеток, только среди клеток без `PREMISE_LEADER` / `PREMISE_LAST`, в строку добавляется «(беда — все варианты с потерей: игрок выбирает меньшее зло ...)»; **«платный»** — ~треть клеток любой завязки (может совпасть с бедой — «заплатить, чтобы откупиться»), в строку добавляется «(один вариант платный — cost, без threshold)». На клетках без пометки «платный» промпт запрещает `cost`.

- `assignRegionNames(cellIds, track, regions)` — край через тот же `regionForDepth`, что у клиента на поле (перенесён в `@trgames/shared`, `games/lucid/track.ts`, вместе с `trackDepths` — BFS-глубина от старта, была локальной в клиентском `trackLayout.ts`). Глубина считается по всему треку, не только по клеткам-событиям.

Тексты короткие: событие — 1–2 предложения до ~140 символов, вариант — одно действие глаголом до ~50 (в схеме потолки 200 и 80 с запасом, чтобы перебор модели не отправлял партию на запасную). Промпт явно говорит: край — атмосфера места, завязка — направление события, не готовый заголовок, повторять её название дословно в `title`/тексте нельзя. Абзац «чаще мешай лидеру, помогай отстающему» заменён отсылкой к клеткам с пометкой FIRST/LAST — перекос теперь опирается на раскладку кода, а не только на память модели о примерно сказанном в начале промпта. Ники игроков — контекстом через `describeNicknames`: «В партии играют: …», с оговоркой, что событие может выпасть любому игроку, поэтому игрока по нику упомянуть можно, а писать, будто событие происходит именно с ним, нельзя; без ников абзац не добавляется. Абзац «только у трети событий один вариант платный» заменён отсылкой к пометке «платный» (мягкая просьба в начале промпта дала 62% вместо трети, пометка у клетки — работает, как FIRST/LAST). Баланс вариантов — просьбой, код не проверяет, коротким списком пунктов: ни один вариант не лучше остальных очевидно; платный даёт примерно на 1–2 больше цены и не приносит Ресурса больше цены (в беде — откуп, без прибыли); рискованный при удаче даёт больше платного, провал ощутимый (−1…−3 клеток, или −2…−4 Ресурса, или пропуск хода); пропуск хода как провал допустим при любом threshold, в остальных ветках — только при threshold ≤ 3 или крупной награде; обычные события не обязаны быть сплошь в плюс — вариант с потерей ради выгоды допустим; текст варианта намекает на последствия без чисел — игрок их не видит до раскрытия (3). Явная оговорка следом: правила примерные, вероятности и средние по ним не считать, каждое событие цифрами не перепроверять — добавлена вместе с выключением рассуждения (4.5, `docs/lucid/MODELS.md`, «Замер 3»), чтобы модель без скрытого слоя рассуждения не тратила выходные токены на то же самое явно. JSON-пример показывает два события разной структуры (риск+платный, риск+бесплатный без платного), а не один шаблон на всех: первая версия примера с одним событием на три варианта (риск/платный/бесплатный) модель копировала буквально — платный вариант вышел у 48 из 48 событий в замере вместо трети (найдено в ревью, `docs/lucid/MODELS.md`, «Замер 3»). Текст перед примером прямо предупреждает: структуру примера как шаблон для всех событий копировать нельзя, иначе платный окажется у каждого. Диапазоны `value` — из `ATOM_RANGES`, промпт также прямо говорит, что `value` не бывает 0 ни у одного атома, кроме `SWAP_WITH_FIRST` (там он всегда 0) — без этого модель изредка присылала бессмысленный нулевой эффект. Для `SWAP_WITH_FIRST` `describeAtoms` (`prompt.ts:25-33`) явно говорит «target всегда SELF, value всегда 0» — раньше про `target` умалчивалось. `condition`/`otherwise` схема допускает, промпт не объясняет — модель их не присылает. Язык — русский по языку промпта, явной инструкции нет.

### 4.4 Схемы

Валидация — zod, `z.strictObject`. `z.toJSONSchema` (`generation/model.ts:55`) → `responseFormat: json_schema`, маршрутизация сужена `provider.requireParameters`. Провайдер гарантирует форму ответа, не диапазоны — их ловит своя валидация (`schema.ts:6-84`):

| Поле | Значение |
|---|---|
| `MOVE` / `RESOURCE` / `SKIP_TURN` / `SWAP_WITH_FIRST` | −4…4 / −5…5 / 1…2 / 0 |
| `threshold` / `cost` | 2…6 / 2…5 |
| регионов / имя региона | 3…5 / ≤24 знаков |
| название ресурса | одно слово без пробелов (дефис можно), ≤20 знаков (`RESOURCE_NAME_MAX`) |
| название карты / строка настроения | ≤30 / ≤70 знаков; `cards` необязателен и в схеме не строгий (`z.unknown()` с `catch`): кривой список или кривая запись мир не рушит, `pipeline.ts` проверяет каждую запись отдельно (`cardNameSchema`) и отбрасывает негодные записи и ключи не вида `card1`…`card25` (позиция в списке даёт id карты), недостающие берут запасное название |
| палитра | 3…6 цветов `#rrggbb` |
| текст / заголовок / вариант | ≤200 / ≤80 / ≤80 |
| атомов в эффекте / вариантов в событии | 1…3 / ≤3 |

Номера клеток схема не проверяет — сверяет `generation/pipeline.ts` (4.6).

### 4.5 Модель и провайдер

OpenRouter. `DEFAULT_MODEL` — `deepseek/deepseek-v4.1-flash:nitro` (`generation/model.ts:22`, заказчик выбрал 2026-09-22, в коде с `aae7a0e`), переопределяется `LUCID_MODEL` из `server/.env` (`model.ts:42`). Ключ — `OPENROUTER_API_KEY` (`model.ts:33`). Рассуждение (reasoning) выключено в каждом запросе — `reasoning: { effort: 'none' }` в `chatRequest` (`model.ts`, поле рядом с `provider`): у `deepseek/deepseek-v4.1-flash:nitro` оно включено по умолчанию и без этого съедало ~85% выходных токенов куска (10k из ~11-12k на 6 событий), а не сам разброс эндпоинтов `:nitro` регулярно выбивал партию на запасной контент. Подтверждено прямым вызовом `generateJson`: `usage.completionTokensDetails.reasoningTokens === 0` (замер 3, `docs/lucid/MODELS.md`). Выключено в коде, не через `LUCID_MODEL`: параметр не специфичен для конкретной модели так, как её id. Сравнение моделей и обоснование — `docs/lucid/MODELS.md`.

### 4.6 Скорость

Пачки `EVENTS_CHUNK_SIZE=6` параллельно; бюджет `GENERATION_BUDGET_MS=180_000` (3 мин, `init.ts:24`, снижено с 7 `aae7a0e` — перекрывает худший замер партии примерно в 1.25 раза и не держит игроков у экрана при зависшем запросе), общий `AbortController` рвёт всё по дедлайну; `MAX_ATTEMPTS=3` на запрос.

|---|---|---|---|
| `:nitro` / без nitro, одиночные запросы | 4.5 с / — | 10–27 с / 12–307 с | $0.004–0.009 за кусок / ~6 мин партия, `sort:'throughput'` хуже |

Промпт теперь называет число событий партии отдельной фразой. Полный разбор — `docs/lucid/MODELS.md`.

### 4.7 Запасная партия

Срабатывает при провале «Мира» или куска «Наполнения» в бюджете — вся партия на запасную, миры не смешиваются; то же при исключении.

`generation/fallbackContent.json`: мир «Станция «Полынь»», `mood: DARK`, 4 региона, 48 событий, собраны по тем же правилам, что и промпт (4.3): тексты событий ≤140 символов, вариантов ≤50; платный вариант у трети событий (16 из 48), «беды» (ни один вариант не даёт чистого плюса) у четверти (12 из 48), провалы ощутимые (−2…−3 клеток, −2…−4 Ресурса, пропуск хода); цены 2–5, награды Ресурсом до +5 (пул пересчитан ×2 под экономику второй версии); условия — только по `RESOURCE`. Пул остаётся 48 событий, а на треке для двоих событий 33 (35% внутренних клеток без порталов; 19–33 на 6…2 игроков), поэтому в игру попадает часть пула; тесты долей и валидации берут весь пул из 48. По `computeContentMetrics`: платных 0.33, бед 0.25, против лидера 0.27, в помощь последнему 0.33, средняя длина текста события 88, варианта 26 символов; тест `fallback.test.ts` держит длины и доли платных и бед. `loadFallbackContent` тасует пул от `${seed}:fallback`. Схема (4.4) в рантайме не накладывается — проверяет только тест `fallback.test.ts:18-33`.

Честность: строка «Придумать ваш мир не получилось, играем на запасном» при `usedFallback`, от игры, остаётся в ленте.

### 4.8 Учёт токенов и стоимости

Решение заказчика («Полный учёт трат и отчёт командой», `OPEN-QUESTIONS.md`) реализовано: две таблицы вместо одной сводной (`de93753`, вытеснено). Старая `usage` (`storage/db.ts:101-109`) не удалена — в локальных базах уже есть, — но новый код в неё не пишет.

`generation_calls` (`storage/db.ts:111-124`, индекс на `party_uuid` — `storage/db.ts:128`) — строка на каждый вызов модели: партия, стадия (`world`/`events`), модель, номер попытки, токены, стоимость, длительность, исход (`ok`/`invalid`/`error`), текст ошибки. Пишет колбэк `onCall` (`pipeline.ts:127,152`, зовётся из `request()`) сразу по завершении вызова, а не по итогу генерации — учитывается и кусок, долетевший в `Promise.all` уже после того, как генерация ушла на запасную партию; раньше такие токены терялись молча (`OPEN-QUESTIONS.md`).

`generations` (`storage/db.ts:130-144`) — одна строка на генерацию, удачную и запасную: модель, время, сколько событий просили, сколько вызовов и перегенераций (вызовы сверх одного на запрос), доли содержания итоговой партии (доля событий с платным вариантом, с эффектом против лидера, с эффектом в помощь последнему — чистая функция `computeContentMetrics`, `generation/contentMetrics.ts`), и `world_name` — своя колонка, не джойн на `parties`: строка партии пропадает уборкой (5.6) раньше, чем кто-то откроет отчёт.

Обе записи обёрнуты `recordStats` (`init.ts:138-165`): сбой записи (диск, sqlite) — это `console.error` с префиксом `lucid:`, генерация или старт партии не откатываются и не уходят на запасной контент.

Отчёт — раздел 8.

### 5.2 Модель движка

Чистые функции над `G` (данные партии) и `ctx` (фаза, очередь). Единственный вход — `applyMove` (`core/reducer.ts`): сверяет `stateId`, фазу и что ходит `ctx.currentPlayer`; при несовпадении отдаёт то же состояние без объяснения.

Сидированный ГПСЧ (mulberry32) — `{seed}` в `G.random`; трек и кубик — разные потоки. Архитектура — ADR-0002 (сервер авторитетен), ADR-0006 (без игрового движка), ADR-0007 (встроена в TRGames второй игрой); обоснования — раздел 9.

### 5.3 Транспорт

Два неймспейса на `io`: `/lucid/lobby` — только `create-party`, короткоживущий; `/lucid` — партия целиком, рукопожатие несёт `partyId`/`playerId`/`nickname`, `namespace.use` находит партию, `party.join()` — отказ как `connect_error`.

Комнаты: `<partyId>` — все соединения партии, общая лента (`append-ribbon`); `player:<partyId>:<playerId>` — соединения игрока, личный вид (`update-party`) и ошибки (`show-error`).

Личная комната несёт `partyId` (фикс `18bfe80`): раньше `player:<playerId>` была общей на весь неймспейс, вторая партия того же браузера получала чужую рассылку.

Комната на партию, не неймспейс — ADR-0008: `connectionStateRecovery` (30 с) восстанавливает комнаты сокета; неудача восстановления — просто полная пересылка вида (клиент не ходит оптимистично). CORS — раздел 8.

### 5.4 Протокол

**Клиент → сервер**

| Событие | Payload | Проверки | Что делает |
|---|---|---|---|
| `create-party` (`/lucid/lobby`) | — (колбэк) | `playerId` из query | `group.create`, персист, таймер удаления; колбэк `partyId`/ошибка |
| `find-party` (`/lucid/lobby`) | `code: string` (колбэк) | `trim`, ровно 4 цифры | `group.findByCode`; колбэк `partyId` или ошибка `lucid.errors.partyNotFound` |
| `propose-theme` | `theme: string` | `LOBBY`, участник, ≤200 симв. | сохраняет предложение, `hasAnswered = true` |
| `decline-theme` | — | те же | очищает предложение, `hasAnswered = true` |
| `start-party` | — | `ownerId`, `canStart` (≥2 игрока) | генерация (4, бюджет 180 000 мс), досрочно «Мир», `setupParty` → `PLAYING` |
| `make-move` | `TMove` (`ROLL`/`CHOOSE_BRANCH`/`CHOOSE_DIE { dieIndex }`/`CHOOSE_OPTION`/`CHOOSE_LAW { index }`/`PLAY_CARD { uid, targetId? }`/`END_TURN`/`BUY_CARD { index: number | null, discardUid? }`/`OPEN_SAFE { bonus }`) | `stateId`/фаза/очередь — в `applyMove`; `CHOOSE_DIE` — только в фазе `DICE`, пока `lastRoll.pending`; `CHOOSE_LAW` — только в фазе `LAW`, `index` — целое, индекс в `G.cards.lawDraw` (после — закон в левой ячейке, ход идёт дальше); `BUY_CARD` — только в фазе `SHOP`, `index` — `null` или целое индекс в `G.cards.shopOffer`, хватает 3 Ресурса, при полной руке нужен `discardUid`; `PLAY_CARD` и `END_TURN` — только в фазе `CARDS`, `uid` — целое, карта из руки ходящего, играбельная (`canPlay`); `OPEN_SAFE` — фаза `ROLL`, игрок на финише, `bonus` целое 0…2, хватает Ресурса; `ROLL` на финише отклоняется | применяет ход; отказ — то же состояние, причина в `console.warn` сервера |
| `play-again` | — | нет | новая партия тем же составом, `nextPartyId` у старой |

Обработчики — через `guard()`: успех → `persist`+`broadcast`; ошибка → `show-error` вызвавшему.

**Сервер → клиент**

| Событие | Payload | Кто получает |
|---|---|---|
| `update-party` | `TPartyView`: `code`, фаза, лобби, тема, `TStateForPlayer?`, `usedFallback`, `nextPartyId` | Лично каждый, `player:<partyId>:<playerId>`, на каждый `broadcast()` |
| `append-ribbon` | `string[]` — прирост журнала | Вся партия, `<partyId>`, только если прирост не пуст |
| `show-error` | `{ message: string }` | Только вызвавший, личная комната (в лобби — тот же сокет напрямую) |

«Партия не найдена» через `show-error` не идёт — бросается в middleware, приходит как `connect_error`.

### 5.5 Граница секретности

`core/formatForPlayer.ts` — явный список полей `G` (`Omit<TG, 'log' | 'random' | 'events'> & { events: Record<number, TEventView> }`): новое поле без упоминания здесь ломает сборку.

Уходит: `players`, `order`, `track`, `theme`, `visited`, `winner`, `branchChoices`, `pendingSteps`, `lastRoll`, `cellHistory`, посещённые `events` — но не сырым `TEvent`, а урезанным `TEventView`: у варианта видны `text`/`threshold`/`cost` всегда, `success`/`failure` — только по раскрытой ветке (3). Руки (`G.cards.hands`) и выложенные карты Лавки (`shopOffer`) видны всем: `cards` уходит как `{ laws, lawDraw, shopOffer, hands }`. Не уходит никогда: `G.cards.shopDeck`, `G.cards.shopDiscard`, колода и сброс законов, `G.random`, `G.log` целиком, непосещённые события, нераскрытые ветки вариантов.

Ник игрока — не секрет и уже лежит в `TPlayer.nickname`, внутри `players` выше. Старые снимки партий в базе могут нести лишнее поле `role` у игрока: состояние читается как есть (`JSON.parse`, без схемы), поле ни на что не влияет.

### 5.6 Жизнь партии

| Этап | Что происходит |
|---|---|
| Создание | `create-party` → `LOBBY`, персист и таймер удаления сразу |
| Вход | Только в `LOBBY` (иначе `party-already-started`); известный `playerId` — в любой фазе |
| Старт | Только `ownerId`, `canStart`; жеребьёвка темы, генерация, `setupParty` |
| Конец | удачный `OPEN_SAFE` на финише → `ENDED` внутри редьюсера (3, «Сейф на финише») |
| Обрыв/возвращение | `disconnect` гасит связь только при опустевшей личной комнате |
| Автопилот | Один на партию; `syncAutopilot()` заводит/снимает `AUTOPILOT_DELAY_MS=30000` на неподключённого `currentPlayer` |
| Удаление партии | `cleanup.sync()`: без подключённых — `CLEANUP_DELAY_MS=300000` (5 мин), повтор не перевзводит |
| Сыграть ещё | Новая партия тем же составом; `nextPartyId` у старой |
| Рестарт сервера | `group.get()` при промахе поднимает `TPartySnapshot` из базы, участники отключены принудительно |

Старт партии (`8fa7ab1`+`e49fd68`): `.catch` на `party.start(...)` в `init.ts` ловит то, что раньше улетало необработанным отказом промиса и роняло весь процесс вместе с Cryptoz. Партия, не дошедшая до `PLAYING`, откатывается `Party.abortStart()` — фаза обратно в `LOBBY`, тема, `usedFallback` и `state` сброшены — и получает строку `lucid.ribbon.startFailed`; партия, уже идущая, — только запись в лог. `PartyGroup.save` не пишет партию, которой уже нет в группе, — защита от воскрешения удалённой партии из базы.

### 5.7 Хранение

`node:sqlite`, путь `LUCID_DB_PATH ?? 'lucid.db'`, обобщено по типу документа (`createStorage<TDocument>`).

| Таблица | Поля |
|---|---|
| `parties` | `uuid TEXT PRIMARY KEY`, `code TEXT` (индекс; 4 цифры, уникален среди живых партий), `theme TEXT NOT NULL`, `state TEXT NOT NULL`, `updated_at INTEGER NOT NULL` |
| `usage` | не пишется новым кодом, оставлена ради баз, где уже есть (см. ниже) |
| `generation_calls` | `id`, `party_uuid`, `stage`, `model`, `attempt`, `input_tokens`, `output_tokens`, `cost_usd`, `duration_ms`, `outcome`, `error_message`, `created_at`; индекс на `party_uuid` |
| `generations` | `id`, `party_uuid`, `model`, `used_fallback`, `duration_ms`, `requested_events`, `calls_count`, `retries_count`, `paid_option_share`, `anti_leader_share`, `help_last_share`, `world_name`, `created_at` |

Код генерирует `PartyGroup.create` (`randomInt`, повтор при занятости); брошенные партии удаляет cleanup, поэтому коды переиспользуются. Колонка `code` добавлена миграцией через `PRAGMA table_info`; у старых партий её нет, `fromSnapshot` берёт `''`, клиент не показывает пустой код.

`state` — `TPartySnapshot` целиком в JSON (секретов нет — `G.random`/`G.log` внутри). `theme`-колонка дублирует `snapshot.theme?.name` — шов модерации, ADR-0005.

Пишется на ход, после генерации, на соединение, в `play-again`. Читается только при промахе `PartyGroup.get()`. Удаляется только из `cleanup` по отсрочке (5.6), не опустевшие не подчищаются — решено не удалять, пока не станет заметно.

`usage` — механика `de93753`, вытесненная `generation_calls`/`generations`: таблицу не удаляем (старые базы уже её открывали), просто не пишем. `world_name` в `generations` появился позже самой таблицы — открытие базы, где колонки ещё нет, мигрирует её через `ALTER TABLE` (`storage/db.ts:147-156`), проверено на копии старой схемы в тестах. Обе новые таблицы и учёт трат — раздел 4.8.

    ├─ Hud (столбик в `main`: шапка → слот с полем → нижняя панель; модалки EventCard и CardPick лежат поверх `main`) →
    │   Board в слоте (клик по клетке из branchChoices → onSelectCell; по посещённой клетке с историей → onViewCell); LawsStrip (полоса трёх ячеек законов в шапке под списком игроков), Die (одна или две грани), Ribbon, EventBar — первой строкой нижней панели (свёрнуто) / EventCard (развёрнуто) → OptionButton × N; CardPick (полноэкранная модалка выбора карты: в фазе LAW у ходящего — закон из `cards.lawDraw`, ход `CHOOSE_LAW`; в фазе SHOP у ходящего — Лавка: карты `cards.shopOffer` с названием мира и строкой `flavor` курсивом, «Купить» неактивна при Ресурсе меньше 3, «Ничего не беру» шлёт `BUY_CARD { index: null }`; при полной руке второй `CardPick` «Рука полна: что сбросить?» шлёт `BUY_CARD { index, discardUid }`; чужой ход — текст «{ник} в Лавке»), Hand (ряд карт своей руки над кнопкой хода: нажатие на чип раскрывает правило; в фазе CARDS у активной карты не из `turn.used` — «Применить» → `PLAY_CARD`; у «Толчка» затем кнопки с никами игроков не у сейфа → `PLAY_CARD { uid, targetId }`; в фазе CARDS в нижней панели «Закончить ход» → `END_TURN`). Названия законов и карт берёт `LucidShared.cardName(G, id)`: название мира, иначе встроенное). Событие, вытянутое законом, приходит в `turn.lawEvent` и открывается в `EventCard` как обычное
    ├─ view.phase === ENDED → Ending
    └─ viewCellId задан → CellView (просмотр клетки, свой стейт в PartyPage, не связан с Hud)
```

`themeStyle` считается раз на смену темы, на корневом `<main>` — смена фазы оформление не сбрасывает.

Строка игрока в шапке `Hud` — одна кнопка на всю ячейку: `● ник · {Ресурс} · карт {N} · связь потеряна`. Точка стоит только у ходящего. «карт N» видно, только если N больше 0. Ресурс и «карт N» не сжимаются. Ник обрезается многоточием. Строка — обычный `flex-wrap`.

Тап по строке (в том числе своей) открывает `PlayerView` (`PartyPage/components/PlayerView/index.tsx`) — полноэкранную модалку в стиле `CellView` (`absolute inset-0 z-20`, фон `--lucid-veil`, «Закрыть», закрывается и по `Escape`). Состояние «какой игрок открыт» живёт в `Hud` (`viewedPlayerId`), модалка лежит последней из оверлеев, поверх карточки события и окна карт, и читает игрока из текущего `state`, поэтому обновляется вместе с партией. Содержимое: ник целиком, роль целиком, `{resourceName} {resource}`; состояния только когда есть («пропускает ходов: N», «ждёт беду», «связь потеряна», «у сейфа»); «Рука» — для каждой карты название (`cardName`), строка `flavor` курсивом, правило, пометка «активная · 3» или «пассивная»; пустая рука — «Карт нет». Кнопок действий нет. Обрезанное название мира в шапке — по-прежнему `Hud/components/TruncatedText` с поповером.

### 6.4 Поле

**Раскладка трека** (`lib/lucid/trackLayout.ts`): `perRow` 4–14 по минимуму отклонения пропорции; змейка — чётные ряды слева направо, нечётные обратно; развилка — прядь со сдвигом по Y. Шаг клетки 132, шаг ряда 150, клеток в ряду 4–14.

**Типы клеток на поле** (`lib/lucid/cellLook.ts`, `cellLook(cell, isVisited)` → `{ shape, fill, icon?, label? }`; форму и цвет выбирает чистая функция, `Board` только рисует; эталон — вариант «В» в `docs/lucid/mockups/cells.html`): у каждого типа своя форма. Нераскрытое событие — полый ромб (радиус 25) со знаком «?», посещённое — ромб, залитый цветом края; пустая — малый круг (r 9), полый, после посещения залитый; зелёная `#5a9e4b` и красная `#c8553d` — круг r 18 своего цвета с белыми «+» и «−», независимо от посещения; Лавка (`SHOP`, `#3f7cc4`) — домик с белой сумкой; закон (`LAW`, `#c9a227`) — шестиугольник r 24 с белыми весами; портал — двойное кольцо цвета своей пары (`#8e5bd0` / `#2f8fd8`, `pair % 2`) с номером пары `pair + 1` в центре; старт и финиш — квадрат с флагом и сейфом. Лавка и закон видны сразу. Формы-пути (ромб, домик, шестиугольник, плитка края) склеены в один `path` на вид (`Board/linkPath.ts`), круги и пиктограммы (обводкой, скруглённые концы) — отдельные элементы; пиктограммы и знаки на телефоне растут вместе с подписями, не больше чем в 1,25 раза. Цвета красной, зелёной и порталов фиксированные, не из палитры темы. Под клеткой финиша подпись «Сейф · 5+» (`SAFE_LABEL`, порог из `LucidShared.SAFE_THRESHOLD`), её места тоже занесены в `busy`. Подпись зоны «2 кубика · выбор» (`ZONE_LABEL`) стоит под первой клеткой зоны `PICK` (`zoneStarts`; вторая и третья трети — одна зона, подпись одна; у зоны `ONE` подписи нет); подписи края мира обходят их — они идут в список занятых мест `busy`, чтобы не накладываться (`57348a8`).

**Облик «грубые изразцы»** (`Board/index.tsx`, сверено с макетом заказчика — совпадает, кроме итоговой таблицы расхождений): лента 30, плитка события 36×28, старт/финиш 42, заливка пройденной плитки 0.95, подложка края 0.07 (2.5× шире ленты), прочерчивание трека 1400 мс. Скругление — обводкой, не радиусом.

**Регионы** (`lib/lucid/regions.ts`): `regionForDepth` (`@trgames/shared`, общая с сервером — 4.3) делит путь по глубине, не по содержимому — секрет до посещения. `ribbon`=цвет+основа→контраст 3:1; `ink`→контраст 4.5:1; `hollow` (непройденная)=основа+`ribbon`, сплошным цветом, не SVG-прозрачностью (`fillOpacity` жёстко `1`) — пройденная плитка (0.95) тут исключение. Гарантии проверены тестом на недружественных цветах (`regions.test.ts`); без регионов путь — одной линией.

### 6.5 Цвет

`lib/lucid/colors.ts` (`deriveRoles`): hex парсится, мусор — прочь, пусто→`FALLBACK_PALETTE`→OKLCH→`base` (под `mood`)→`text` (контраст 4.5:1)→`accent` (насыщенный, контраст 3:1)→`supports` (остаток). `ensureContrast`: квантует под 8 бит, шагает светлотой OKLCH 1% к чёрному/белому; крайний случай — чёрный/белый (≥4.58:1).

Тест на недружественных палитрах (`colors.test.ts`) гарантирует: партия физически не может выдать нечитаемый экран (DESIGN.md, «Вывод ролей»). `theme.ts`: переменные `--lucid-base/text/accent/line/muted/veil`, фон — градиенты из хеша названия мира на клиенте. ```bash

yarn workspace @trgames/client dev          # только клиент, Vite

```

Порты: клиент 3000, сервер 4001 (захардкожен, `server/src/index.ts`, не переопределяется), Storybook 6006.

| Файл | Переменная | Назначение |
|---|---|---|
| `server/.env` | `OPENROUTER_API_KEY` | ключ OpenRouter; при отсутствии — пустая строка |
| `server/.env` | `LUCID_MODEL` | модель генерации; при отсутствии — `DEFAULT_MODEL` из кода |
| `client/.env` | `VITE_API_BASE_URL` | инжектится как `__API_BASE_URL__` |

Значения переменных в документы не выносим. `server/.env` грузится своим парсером (`loadEnv()`) первой строкой `index.ts` — `node --env-file` не пробрасывается через `nodemon`.

CLI-флагов у сервера нет: CORS origin берётся из `CORS_ORIGIN` в `server/.env`, пусто — `*`. Клиент без `VITE_API_BASE_URL` ищет сервер на хосте страницы, порт 4001.

Скрипты вне `server/src` — с `TS_NODE_COMPILER_OPTIONS='{"module":"commonjs","moduleResolution":"node"}'`, иначе `ts-node` резолвит модули иначе, чем основной процесс.

Грабли окружения — раздел 7.
